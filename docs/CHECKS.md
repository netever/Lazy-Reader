Обозначения статуса:

## Найдено и исправлено в фазе 0

Эти ошибки видны только в настоящем Android WebView. На macOS и в Chromium их не было или они не проявлялись.

1. **Импорт падал на Android** («expected a binary body»). Tauri на Android передаёт вызовы через `postMessage` с JSON, двоичное тело не поддерживается. `Uint8Array` превратился бы в JSON-массив чисел. Теперь на Android куски по 1 МБ идут в base64, на компьютере — двоичные по 4 МБ. Ответы с байтами (чтение книги и диапазонов PDF) Tauri отдаёт отдельным запросом, они работают.
2. **PDF не открывался в WebView 133.** Современная сборка PDF.js 6.4 использует `Map.prototype.getOrInsertComputed`. Перешли на legacy-сборку с полифилами (ADR 0006). На слабых телефонах WebView часто старый.
3. **Бесконечный цикл ResizeObserver после закрытия книги** (~60 ошибок в секунду, процессор работает впустую). React удаляет DOM раньше, чем вызывает очистку `useEffect`. foliate-js при закрытии не мог снять наблюдение с `<body>` раздела, потому что у отсоединённого iframe нет документа. Теперь книга закрывается в очистке `useLayoutEffect`, пока DOM на месте. Проверено на EPUB, `.fb2.zip`, CBZ: 0 ошибок.
4. **Позиция «уезжала» назад** при перезапуске и смене шрифта: строка состояния внизу меняла высоту, страницы переразбивались, а сохранялось начало новой страницы. Строка теперь фиксированной высоты, а позиция не перезаписывается, пока сохранённая точка видна на экране.
5. **`since_process_ms` не считался на Android**: приложению запрещено читать `/proc/uptime`. Теперь берётся `CLOCK_BOOTTIME`.
6. **FB2 не показывался в системном выборе файлов Android.** Фильтр `accept` по расширениям Android переводит в MIME-типы, а у `.fb2` известного типа нет. На Android фильтр снят, формат проверяется при импорте.

## Замечания к foliate-js (не исправлено, сообщить автору)

- `Paginator` наблюдает за своим `#container`, а в `destroy()` снимает наблюдение с самого себя (`paginator.js`, строки 558 и 1122). Наблюдатель за отсоединённым контейнером остаётся, это небольшая утечка памяти на каждую открытую книгу. Цикла не вызывает.

## Большой PDF (≈300 МБ, 600 страниц)

PDF.js получает файл кусками по 256 КБ через `read_book_range`. Интерфейс при открытии не блокируется: разбор идёт в воркере. Поведение зависит от устройства самого PDF:

| Файл | Дерево страниц | Прочитано при открытии (Chromium) | Эмулятор: документ готов / первая страница / память процесса |
| --- | --- | --- | --- |
| `big-tree.pdf` | Сбалансированное, по 10 страниц (как у LaTeX, Word) | 27 запросов, 6,6 МБ; дальше ~0,3 МБ на страницу | 0,40 с / 0,47 с / 133 МБ |
| `big.pdf` | Плоское, 600 страниц в одном `/Kids` (как у многих сканеров) | 1204 запроса, ~315 МБ — весь файл | 1,39 с / 1,43 с / 278 МБ |

**Вывод.** При открытии PDF.js проверяет последнюю страницу и при плоском дереве загружает объекты всех страниц. Если между ними лежат картинки, это весь файл, и он остаётся в памяти воркера. На слабом Android с 2–3 ГБ памяти это риск нехватки памяти. Варианты для фазы 1: предупреждение для таких файлов или своя быстрая проверка структуры перед открытием. Проверить на реальных сканах владельца.

**Импорт 295 МБ на Android занимает ~35 с** из-за base64 через JSON. Для фазы 1: копировать файл нативно (content URI → Rust или Kotlin) без передачи через WebView.
